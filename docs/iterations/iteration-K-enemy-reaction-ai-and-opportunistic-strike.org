* Context (why this sprint exists)
Defensive reactions are now GENUINELY live for the PLAYER: an enemy Strike opens the two-phase
pop-ups (Dodge/Steel on-attacked, Parry/Block on-hit), a successful Dodge relocates Titus (with the
legal hexes highlighted), Block reduces by 1[W]+block_value, Parry rolls d20+attack_bonus+parry_bonus,
and the rich combat log shows it all. But TWO halves of the reaction system are still stubs:
1. The ENEMY never reacts. On the player-strikes-enemy path the enemy always Passes ("none") — the
   AI has no defensive brain. (Deferred from Iteration I as Part B / FR-006/FR-007.)
2. NOBODY gets an Opportunistic Strike. An adjacent hostile Striding away provokes nothing — the
   legality exists in reaction_window.gd but no trigger is ever emitted and no effect is resolved.
   (Deferred from Iteration I as Part C / FR-008/FR-009.)

This sprint finishes the reaction system: give the enemy a deterministic defensive policy (Part B),
then add the movement-triggered Opportunistic Strike for BOTH movers (Part C). Full prior scope lives
in docs/iterations/iteration-I-deferred.org; this brief supersedes it with launch-ready detail +
the guardrails the reaction work has repeatedly needed.

⚠️ HARD-WON LESSON THIS BRIEF EXISTS TO ENFORCE: the reaction system has shipped "green tests, dead
in play" FIVE times (H Gap#1, FEAT-006, J DEF-001, J-R2 Dodge-Step, and the Block/Parry weapon-dict
gaps). The root cause is ALWAYS the same: the logic/data is correct and a test asserts THE FUNCTION,
but nothing wires it into the live composition root, and the test passes anyway because it calls the
internal method directly instead of driving the REAL trigger path. The most recent (2026-07-10):
_resolve_dodge_step_prompt() was fully built + capstone-tested, but advance_ai_turn() never called
it — every test invoked the prompt directly. Part B (enemy AI on the player-strike path) and Part C
(movement-triggered windows) are BOTH exactly this shape. The guardrails below are the heart of the
brief.

* PART B (P1) — Enemy reaction AI policy (player-strikes-enemy path)
** Live-path gap
On the player-strikes-enemy path (MainScene _verb_bar_strike_execute → resolve_action_use_case.resolve),
active_defense is hardwired to "none" — the enemy never opens a reaction window, so it always eats the
full hit. The two-phase reaction machinery (PreHitAvoidance Dodge/Steel + OnHitMitigation Parry/Block)
that round_session.advance_ai_turn() runs for the PLAYER defender has no mirror on this path, and the
enemy has no chooser. Additionally, the enemy weapon dict (MainScene enemy-combatant build) + EnemyResource
/ skeleton.tres carry NO parry_bonus / block_value / block_die — so even if a window opened, is_parry_eligible
/ is_block_eligible read 0 and Parry/Block would be filtered out (the SAME composition-root data gap that
shipped the player's Parry/Block dead until commit cca639e).

** Fix — three coupled pieces (all required; none ships alone per G4)
1. ENEMY DEFENSIVE DATA — the Skeleton wields an ARMING SWORD (✓ Guy 2026-07-10, from the
   docs/hollow-world-v0-spec.org weapons table). Add parry_bonus / block_value / block_die to
   EnemyResource (mirror WeaponResource's fields + the "block_die <= 0 ⇒ fall back to damage_die"
   contract the player fix established) and thread them into MainScene's enemy-combatant weapon dict
   build (mirror the player weapon dict — this is the composition-root data gap that shipped the
   PLAYER's Parry/Block dead; the enemy must not repeat it). Set skeleton.tres's weapon to the Arming
   Sword's TABLE values:
     - damage_die = 6 (1d6 S), proficiency_bonus = 2, block_value = 2, parry_bonus = 4,
       block_die = 0 (no Block-die property ⇒ Block rolls the 1d6 damage die → Block reduces by
       1d6 + 2), damage_modifier_attribute = strength (unchanged).
   The Skeleton's Mobility skill is already correct (skeleton.tres skills.mobility=1 == its dexterity=1,
   i.e. Dexterity + not-yet-existing modifiers, mirroring Titus's mobility=2==dexterity=2 — ✓ Guy). At
   10+1=11 vs AC ~14 the Skeleton will NOT Dodge in live play; that is EXPECTED (higher-Mobility enemies
   come later). Keep the Dodge rule live for those future enemies; the Skeleton only ever Parries/Blocks.
   ⚠ BALANCE NOTE (G7): the Skeleton's weapon proficiency rises from its current +1 to the Arming
   Sword's +2 (its attack bonus goes up by 1). That is the ONE sim-affecting change here (the
   parry/block fields never touch the pass-only sim). It WILL move sim_results.json (win_rate /
   avg_rounds), so this is a DELIBERATE, one-time re-baseline (✓ Guy approved 2026-07-10): regenerate
   sim_results.json and re-pin the provenance test, and record the new win_rate/avg_rounds in the design
   output — NOT a silent regen, and distinct from the forbidden "reaction variance leaking into the sim."
   (DONE 2026-07-10, pre-K: all weapon .tres were reconciled to this table as ground truth —
   longsword block_value 1→3/parry_bonus 2→4, quarterstaff block 1→2, longbow block 0→1 — with their
   dependent tests re-pinned. So the player's Longsword already matches the table entering this sprint.)
2. THE POLICY. NEW infrastructure/ai_reaction_policy.gd implementing
   core/application/ports/reaction_chooser_port.gd's choose(legal_reactions, context) -> String with a
   DETERMINISTIC, seed-stable policy (do NOT reuse infrastructure/auto_reaction_chooser.gd — that is
   only the headless "pass"/"first_legal" double). The rules map onto the TWO reaction windows exactly
   (Dodge is a PRE-hit decision; Parry/Block are POST-hit, once roll_total and damage are known) —
   NOT a single-window precedence (✓ Guy 2026-07-10, exact cutoffs below):

   ┌ PreHitAvoidance window (before the attack roll — roll_total NOT yet known):
   │  • DODGE if  10 + (enemy Mobility skill)  >  the targeted defense value  (the passive defense the
   │    incoming Strike resolves against, i.e. the enemy's AC for a weapon Strike). Rationale: 10+Mobility
   │    is a take-10 Mobility check; if it exceeds the passive AC, Dodging RAISES the enemy's effective
   │    defense (harder to hit), so Dodge is worthwhile; otherwise it lowers it — Pass.
   │  • else Pass (fall through to the OnHitMitigation window if the attack hits).
   └
   ┌ OnHitMitigation window (only if the attack HIT and no reaction was already spent — roll_total and
   │  damage_raw ARE known here):
   │  • PARRY if the Parry has a > 50% chance to succeed. Parry succeeds when d20 + B > roll_total, with
   │    B = parry_attack_bonus + parry_bonus (the defender's full attack bonus + weapon parry_bonus, the
   │    SAME B resolution.gd/apply_on_hit_defense now uses). P(success) = (20 − (roll_total − B)) / 20,
   │    so > 50% is the EXACT deterministic test:  B >= roll_total − 9  (no RNG — a closed-form check on
   │    the already-known roll_total).
   │  • else BLOCK if the Parry chance is <= 50% (i.e. NOT the above) AND the hit is heavy:
   │    damage_raw  >  enemy.hp_current / 4  (more than a quarter of the enemy's CURRENT health).
   │  • else Pass.
   └
   - Budget-aware GATE (applies to BOTH windows): never react below RESERVE = keep >= 1 action for the
     enemy's own next turn; if reacting would break the reserve, Pass regardless of the rules above.
   - Seed-stable: no RNG in the choice itself (the resolution roll still uses the seeded RNG). Surface
     the chosen constants (the 10-take on Mobility, the >50%/≤50% Parry split, the 1/4-HP Block cutoff,
     the ≥1 reserve) in the design output — do not bury them.
   ⚠ DEPENDENCY: the DODGE rule needs the enemy to carry a Mobility SKILL value (EnemyResource.skills,
   added in Iteration G). The Skeleton currently has none/0 → 10+0 vs AC ~14 means it would never Dodge.
   Give the Skeleton a Mobility value if Dodging is desired (Guy to confirm) — otherwise document that
   the Skeleton only ever Parries/Blocks, and keep the Dodge rule live for future enemies.
3. THE WIRING (the piece the trap keeps eating). Give the player-strikes-enemy path the SAME two-phase
   structure advance_ai_turn() has, but driven by the policy SYNCHRONOUSLY (choose(), NO pop-up)
   instead of the player pop-up: open the ENEMY's PreHitAvoidance window (Dodge/Steel) before the
   roll and its OnHitMitigation window (Parry/Block) after a hit, feed each through
   ai_reaction_policy.choose(), thread the chosen active_defense / on_hit_defense into the SAME
   consolidated resolution path (resolve_to_hit → apply_on_hit_defense), spend the enemy's reaction
   via the ActionEconomy, and honor the ≤1-reaction-per-Strike budget rule. Reuse the EXISTING seams
   (resolve_to_hit_uc / apply_on_hit_defense_uc / _build_defense_context — which already computes the
   defender's parry_attack_bonus generically, so it works for the enemy defender for free).
4. ENEMY DODGE-STEP (the enemy-side mirror of R-2 — ✓ Guy 2026-07-10: "the enemy should also pick a hex
   to Step into on a successful Dodge"). When the ENEMY defender's Dodge succeeds (defender_stepped=true
   on the player-strikes-enemy path), the enemy must ALSO Step to a legal adjacent hex and its token must
   move — exactly like Titus does, but the hex is chosen by a DETERMINISTIC AI policy, NOT the player
   pop-up + highlight. Reuse the SAME dodge-step machinery the player path already has
   (round_session._resolve_dodge_step_prompt / ResolveDodgeStepUseCase / the _token_reposition_fn seam +
   _step_hex_query_fn legal-move computation) — do NOT build a second reposition/step path — but swap the
   hex-choice resolver: for an enemy defender inject an AI hex chooser (synchronous, no pop-up, no
   set_selectable_hexes highlight) instead of the player's _UIHexChoiceResolver. The AI hex-choice
   heuristic is DETERMINISTIC/seed-stable (✓ Guy 2026-07-10): the legal adjacent hex that KEEPS the enemy
   in melee reach of its attacker if any such hex exists, else the first legal hex. Surface the rule in
   the design output. If no legal adjacent hex exists, the Dodge still negates the hit but
   no Step occurs (same edge as the player path). NOTE: this is currently un-exercised in live play
   because the Skeleton won't Dodge (low Mobility, piece 1), but it MUST be correct + wired for the
   higher-Mobility enemies coming later — and G1/G2 still apply: prove it with a boot-real test that
   drives a PLAYER Strike, forces the enemy's Dodge to succeed, and asserts the enemy combatant's
   hex_coord + token actually moved to the AI-chosen hex (NOT by calling _resolve_dodge_step_prompt
   directly — the exact trap that shipped the player Dodge-Step dead).
** OBSERVABLE ACCEPTANCE (G1/G2): boot real MainScene; the PLAYER Strikes the Skeleton; assert (a) the

* PART C (P2) — Opportunistic Strike (movement-triggered offensive reaction)
** Already BUILT (do NOT rebuild)
Legality: core/application/reaction_window.gd already returns [opportunistic_strike] for a
{trigger_type:"OpportunisticStrike", attack_context:{melee_reach:true}} trigger (see
REACTION_OPPORTUNISTIC_STRIKE + the "OpportunisticStrike"/melee_reach branch, ~line 659); the choice
constant + the reaction-spend in resume() exist; tests/unit/test_reaction_window.gd pins the legality.

** Live-path gaps (BOTH must land — the second is the real work)
1. TRIGGER EMISSION on the mover's Stride path (symmetric — BOTH movers, Guy-approved). For each OTHER
   combatant that is adjacent to the mover's START hex, hostile, not Spent, and has melee reach: build
   the OpportunisticStrike trigger and open its window BEFORE the Stride mutates position.
   - Enemy mover: core/combat/ai.gd's decide_action executes the Stride as part of a composite
     "Stride-then-Strike" decision — the window must open BEFORE Movement.stride() commits.
   - Player mover: MainScene _verb_bar_stride_execute → movement path, before the Stride commits.
   - Reactor = player ⇒ the real pop-up (turn_controller.resolve_reaction). Reactor = enemy ⇒ the
     Part B ai_reaction_policy decides (so Part C's enemy side DEPENDS on Part B — do B first).
2. EFFECT RESOLUTION (the real gap — resume() only records the choice + spends today, applies nothing,
   the exact G3 anti-pattern). On an opportunistic_strike choice, resolve a melee Strike from the
   reactor against the MOVER through the SAME consolidated resolution path Part A/J established
   (resolve_action_use_case.resolve / resolve_weapon_attack), landing BEFORE the mover's Stride
   commits. Pay via spend_reaction (how resume() already spends), NOT spend_action. Melee-only via the
   existing relaxable predicate.
** Ordering / interrupt semantics (Guy-approved, settled)
Resolve the opportunistic Strike, THEN — if the mover survives and the Stride is still legal — complete
the Stride; if the mover is DOWNED, CANCEL the Stride. Multiple eligible reactors resolve in INITIATIVE
order. ⚠ ASYNC: this adds reaction await point(s) into the movement path (player pop-up) — audit the
coroutine chain the same way J's two-phase await work did.
** OBSERVABLE ACCEPTANCE (G1/G2): boot real MainScene; drive a REAL Stride (Skeleton Strides out of

   Stride verb); assert (a) the reactor's Strike resolved against the mover — the mover's hp dropped —

   Strike CANCELLED the Stride (mover stays put, defeated), (d) with two eligible reactors they fire in
   initiative order. Drive it through the REAL Stride trigger path, never by building the trigger or
