* PART A — P0: Reaction timing correction (Dodge/Steel on-attacked; Block/Parry on-hit)

** The rule (Guy, 2026-07-09)
- Dodge / Steel are ON-ATTACKED reactions: the window opens when the actor is TARGETED, BEFORE the
  attack roll resolves. A successful Dodge (Mobility check) avoids the attack entirely.
- Block / Parry are ON-HIT reactions: the window opens only AFTER the attack roll lands a HIT, to
  MITIGATE damage (Parry: parry-roll > attack roll → negate to 0; Block: reduce by 1[W]+block_value).
  If the attack MISSES, no Block/Parry window opens.
- ✓ BUDGET RULE (Guy 2026-07-09): AT MOST ONE reaction per incoming Strike. If the defender attempts
  Dodge (whether it succeeds or fails), a reaction is spent and the on-hit Block/Parry window does NOT
  open. The on-hit window opens ONLY when no reaction was spent on-attacked (i.e. the defender Passed
  the Dodge/Steel window) AND the attack hits. So a single Strike provokes at most one spent reaction.

** ⚠ KEY FINDING — the resolution MATH already phases this; the WINDOW flow does not
core/rules/resolution.gd resolve_weapon_attack() ALREADY applies Dodge as a PRE-hit Mobility check and
Parry/Block as POST-hit branches (see its own doc: "pre-hit Mobility check" / "post-hit Parry/Block
branch"). The defect is purely at the WINDOW/UI layer: the live path opens ONE window up front
(round_session.gd _build_reaction_trigger → trigger_type "WeaponAttack" → reaction_window.gd's
WeaponAttack case unions Dodge+Parry+Block into ONE pop-up) and passes the single chosen active_defense
into resolve_weapon_attack(). This SUPERSEDES the Iteration-I brief's since-shipped "pop-up opens ONCE
up front" decision — that decision was wrong per the ruleset.

** The re-architecture (Part A's real work; the sprint's highest-risk async change)
On the enemy-strikes-player path (round_session.advance_ai_turn — currently the sole live reaction path):
1. ON TARGETED (before the roll): open a DODGE/STEEL window (new trigger_type e.g. "PreHitAvoidance" —
   union of Dodge + Steel-when-eligible; add the case to reaction_window.gd _compute_legal_reactions
   alongside the existing WeaponAttack aggregation, reusing is_dodge_eligible/is_steel_eligible). If the
   defender Dodges and the Mobility check succeeds → attack avoided; resolve nothing further. If they
   Dodge and FAIL → reaction spent, proceed to the roll but SKIP the on-hit window (budget rule). If
   they Pass → proceed to the roll with the on-hit window still available.
2. RESOLVE THE ATTACK ROLL (hit/miss). The caller must learn the hit result BEFORE applying Parry/Block.
   Today resolve_weapon_attack() takes active_defense up front and sequences internally. ⚠ PROPOSED
   split (CONFIRM with the resolution owner; do NOT duplicate the math): add a two-phase entry —
   resolve_to_hit(attacker, target, weapon, defense_type, pre_hit_defense, ctx) → {hit, crit,
   roll_total, damage_raw, defender_stepped}, then apply_on_hit_defense(partial, on_hit_defense, ctx) →
   {damage_final, active_defense_applied, on_hit_suppressed}. The existing single-call
   resolve_weapon_attack() stays as a thin wrapper over the two (preserving the pinned characterization
   test byte-for-byte for the default/"none" path).
3. ON HIT (roll succeeded) AND no reaction spent on-attacked: open a BLOCK/PARRY window (new
   trigger_type e.g. "OnHitMitigation" — union of Parry + Block-when-eligible). Apply the chosen
   mitigation. On a MISS, or if a reaction was already spent, skip this window.
- Both windows spend via spend_reaction(); the budget rule guarantees ≤1 spend per Strike.
- ⚠ ASYNC: this adds a second await point in advance_ai_turn — audit the coroutine chain exactly as
  Iteration I's FEAT-003 did (the highest-risk edit). Reuse the existing reaction_resolver_fn seam;
  the resolver is called up to twice per Strike now (pre-hit, then on-hit), never more.
