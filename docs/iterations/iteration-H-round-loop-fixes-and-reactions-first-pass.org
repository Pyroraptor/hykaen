* PART A — P0: Fix the round loop (idle enemy never depletes; round never ends; no round 2)

Root-caused from real play (Titus Spent at 0 after 7 one-per-turn Strides — CORRECT;

** A-1: An enemy turn with no productive action must still END THE TURN toward round-end
- DEFECT: core/application/round_session.gd advance_ai_turn() — when core/combat/ai.gd
  decide_action() returns the null-action sentinel (action_type ""), the CWE-835 guard
  does `_advance_cursor()` WITHOUT the actor consuming anything, so the enemy takes free
  no-op turns forever and its budget_remaining never decreases.
- decide_action() returns "" whenever the enemy is out of reach AND no legal Stride gets
  STRICTLY closer (ai.gd _stride_toward_target: best_distance >= current_distance, no
  destinations, or blocked) — a real and common state.
- RESOLVED (Guy approved the Wait action): introduce an explicit WAIT — a new resolvable
  action that spends ONE action from the budget (ActionEconomy.spend_action, no Movement
  trait, no target) and does nothing else. The AI/idle path (ai.gd decide_action returns
  the null-action sentinel) resolves as a Wait, so an enemy with no useful action still
  depletes its budget and becomes Spent in ≤7 turns — keeping the "7 actions per round,
  one per turn" model intact and guaranteeing termination.
- PLAYER side (deliberate design — budget conservation): a human who ends their turn
  WITHOUT choosing an action is a FREE PASS that does NOT spend. Rationale: reactions cost
  budget actions and are gated ONLY by "not Spent" (see the REACTION-GATING note below),
  so letting a player end a turn without spending lets them CONSERVE budget to react later;
  a forced Wait would burn budget they may want to hold (and, at 1 action left, could Spend
  them out of a reaction entirely). Round termination is still guaranteed by the A-2
  no-progress backstop. v0 SIMPLIFICATION: enemies do NOT conserve for reactions — an idle
  enemy always Waits (spends); only the human may hold. (Revisit later if desired.)
- ⚠ REACTION-GATING (already correct — do NOT regress): reactions are gated ONLY by
  remaining budget. ActionEconomy.spend_reaction() checks `_is_spent` and does NOT check
  the per-turn one-action gate (`_action_used`, which lives only in spend_action()). So a
  combatant may react on another combatant's turn REGARDLESS of whether it spent its own
  turn's action — provided it is not Spent. Part B's reaction wiring MUST preserve this;
  reacting is budget-gated, never turn-action-gated.
- TESTS: an out-of-reach enemy that cannot close still becomes Spent within 7 turns; a
  1v1 where the player kites still terminates; no enemy can take more turns than its
  budget allows.

** A-2: Interactive round-end must have a no-progress backstop (parity with the sim)
- DEFECT: is_round_over is true only when _find_next_actionable_index() == -1 (no living
  un-Spent actor; round_session.gd _is_actionable). A non-Spent idle enemy stays
  actionable forever → round never ends → presentation/turn_controller.gd _drive() spins
  advance_ai_turn() up to _MAX_AI_TURNS_PER_DRIVE (1000) then bails → game WEDGED. Titus,
  once Spent, IS correctly skipped — the deadlock is entirely enemy-side.
- NOTE: the AUTONOMOUS sim path already HAS a backstop — run_autonomous_to_completion()
  forces a DRAW when a full cycle resolves zero actions. The INTERACTIVE cursor path has
  NONE. If A-1 (Wait spends an action) is adopted, budgets always deplete and the round
  ALWAYS terminates naturally — but STILL add an interactive no-progress backstop
  (mirror the sim's: if a full pass over all actionable combatants resolves/【spends】
  zero, end the round) so a future zero-cost action can never re-wedge the UI.
- TESTS: a constructed stall (an actor that can neither move nor attack) ends the round
  via the backstop instead of hanging; _drive() never reaches its 1000-guard in normal
  play.

** A-3: Multi-round loop — a round ending without a decided outcome must start the next round
- DEFECT: MainScene.gd is single-round. `const ROUND_NUMBER: int = 1` (line ~196);
  _on_round_over() (line ~1294) only refreshes `outcome` + clears UI — it NEVER calls
  begin_round() again. Comment at MainScene.gd:194 flags "continuation (calling
  begin_round() again once a round ends)" as not-built. So even a correctly-ending round
  just sits at round-over with no round 2.
- REQUIRED: on round-over WITHOUT a decided win/loss (round_session.outcome() == ""),
  MainScene must (1) call round_session.finish() (end_of_round resets every combatant's
  ActionEconomy budget to 7 — verify this already happens in finish()), (2) increment the
  round number, (3) begin_round(next_round, party, enemies) to obtain a fresh RoundSession
  for the SAME surviving combatants at their CURRENT hp/positions, and (4) re-wire
  TurnController/token-reposition to the new session (the SAME composition-root wiring
  MainScene already does once at startup — factor it into a reusable method, do NOT
  duplicate). ROUND_NUMBER becomes a runtime var, not a const.
- On a DECIDED outcome (won/lost), behavior is unchanged (ResultScreen shows terminal
  state; no new round).
- TESTS: a round that ends with both sides alive begins round 2 with budgets reset to 7
  and combatants at their carried-over hp/positions; the round counter increments; a
  round that ends in a win/loss does NOT start a new round; multi-round E2E steel thread
  (round 1 → round 2 → decided outcome) passes headless.

* PART B — P1: Reaction system first pass (Block, Parry, Dodge, Steel, Opportunistic Strike)

Goal: when a reaction TRIGGER fires during live play, the affected combatant may spend a
reaction to respond, chosen through a blocking pop-up (player) or an AI policy (enemy),
and the choice modifies the trigger's resolution — reusing resolution.gd's EXISTING
math wherever it already exists.

** B-0: Reaction WINDOW architecture — resolution must PAUSE for a blocking choice
Guy's UX (authoritative): "When a trigger is satisfied, a pop-up window appears with
legal reactions and the option to just pass without reacting. The player must choose an
option before the rest of the trigger resolves."
- The current resolve() pipeline is synchronous (roll → apply → return). Reactions
  require a PAUSABLE resolution: at each reaction trigger, resolution must (1) compute the
  set of LEGAL reactions for the reacting combatant, (2) YIELD to a chooser, (3) receive
  the chosen reaction (or Pass), (4) continue resolving with that choice applied.
- MODEL IT ON THE EXISTING STEPWISE PATTERN: RoundSession (ADR-007) already turned a
  batch loop into a resumable, human-drivable object. Introduce an analogous small
  reaction-window abstraction (application layer) that exposes the pending trigger +
  legal-reaction list and accepts a choice — do NOT block the engine thread, and do NOT
  put UI/Node types in core/ (ADR-001). Reuse the existing EventSinkPort/RoundEvents
  surface for emitting "reaction window opened" rather than a new port if feasible
  (ADR-002 — flag if a new port is genuinely required).
- The CHOOSER is injected (like AIDecisionPort): a PlayerReactionChooser (Presentation —
  drives the pop-up) for player-controlled reactors; an AI reaction policy for enemies
  (see B-4). The domain never knows which; it only asks the injected chooser to pick from
  the legal set.
- "must choose before the rest of the trigger resolves" = resolution does NOT proceed
  past the window until a choice returns. For headless tests/sim, an auto-chooser
  (Pass, or a fixed policy) stands in — no UI required to exercise the rules.

** B-3: THE FIVE REACTIONS — exact mechanics (4 exist in resolution.gd; add Opportunistic Strike)
Restated from the ruleset (docs/brief.org:315-323) + the EXISTING resolution.gd behavior.
Guy CONFIRMED these mechanics match intent (2026-07-07) — do NOT alter them.
- DEFENSIVE reactions (trigger: the reactor is TARGETED by a Strike). Reaction ordering
  is already encoded in resolution.gd's RNG sequence and phases:
  - DODGE — trigger: attack vs AC or Reflex, reactor NOT Immobilized, an open adjacent
    hex exists to Step into. Effect: substitute a Mobility check (d20+mobility) for the
    passive AC/Reflex as the value the attacker must beat; on SUCCESS (attacker fails to
    beat it) the attack MISSES and the defender Steps 1 hex (defender_stepped=true).
    Pre-hit (rolls before the attack roll).
  - PARRY — trigger: hit by a weapon attack vs AC, reactor wields a weapon with
    parry_bonus. Effect: parry roll = d20 + parry_bonus; if it STRICTLY EXCEEDS the
    attacker's roll_total, damage → 0 (on_hit_suppressed). Post-hit.
  - BLOCK — trigger: hit by a weapon attack vs AC, reactor wields a weapon with a
    block value. Effect: reduce damage by roll(block_die|damage_die, tier) + block_value
    (1[W]+block at T1). Post-hit, cannot go below 0.
  - STEEL — trigger: attack vs Fortitude or Will, reactor conscious. Effect: substitute a
    Determination check (d20+determination) for Fort/Will; on RESIST, +2 to the reactor's
    next check this round (next_check_bonus).
    RESOLVED (Guy): INCLUDE Steel — but it is the DESIGNATED DEFERRABLE item: if the
    sprint is over-full, Steel is the first thing to cut. Steel uses the SAME logic shape
    as Dodge — a Determination check (d20+determination) SUBSTITUTES for the passive
    Fort/Will exactly as Dodge's Mobility check substitutes for AC/Reflex. Build them as
    ONE shared "check-substitutes-for-passive-defense" mechanism parameterized by (skill,
    which passive defenses it covers, on-success effect) — resolution.gd already structures
    Dodge/Steel in parallel, so factor the common core. Steel stays UN-TRIGGERABLE in live
    play until a Fort/Will attack exists (no spells yet): ship it wired + data + unit-tested
    with a dormant trigger.
- OFFENSIVE reaction (NEW — not in resolution.gd):
  - OPPORTUNISTIC STRIKE — trigger: an enemy currently within the reactor's MELEE reach
    (adjacent) performs a STRIDE (NOT a Step — Step provokes no reactions,
    docs/brief.org:286-289). Effect: the reactor makes one melee Strike against the mover,
    resolved through the SAME Strike pipeline (B-2), spending a reaction from its budget.
    RESOLVED (Guy): trigger = an enemy CURRENTLY in the reactor's melee reach (adjacent)
    performs a Stride. TIMING = the Opportunistic Strike resolves BEFORE the move occurs —
    the Strike lands against the mover at its PRE-Stride hex; if it drops the mover, the
    Stride does not happen. MELEE-ONLY: a ranged weapon CANNOT normally perform an
    Opportunistic Strike — BUT implement the melee-only restriction as a RELAXABLE
    eligibility PREDICATE (not a hard architectural impossibility), so a future
    higher-level TALENT can enable ranged Opportunistic Strikes without a rewrite. BOTH
    sides' Strides check for provoked Opportunistic Strikes (player Strides → adjacent
    enemies may react via the AI policy; enemy Strides → the player may react via the
    pop-up). NOTE: Step still provokes NOTHING (docs/brief.org:286-289) — only Stride.
- Reaction ECONOMY (already built, reuse): every reaction costs ONE action from the
  reactor's per-ROUND 7-action budget via ActionEconomy.spend_reaction(); a SPENT
  combatant cannot react (spend_reaction returns ALREADY_SPENT → the reaction is not
  offered). Reactions are out-of-turn and draw from the same shared budget (CR-001).
  ⚠ INTERACTION WITH PART A: a reaction spends a budget action, so reactions ALSO deplete
  a combatant toward Spent — keep this consistent with A-1's Wait/spend model.
  ⚠ CRITICAL PITFALL — reactions pay via spend_reaction(), NEVER spend_action(): spend_action()
  checks the per-turn one-action gate (_action_used — set true once you act on your turn,
  cleared only at start_of_turn) and would WRONGLY block a reaction taken after you already
  acted this turn. spend_reaction() deliberately does NOT check _action_used (only _is_spent),
  so it is the ONLY correct spend path for a reaction. This matters most for OPPORTUNISTIC
  STRIKE, which reuses the Strike pipeline: it must resolve hit/damage via the shared
  resolution math BUT pay through spend_reaction(), NOT the normal Strike's spend_action() —
  else an actor that already took its turn action could never Opportunistic-Strike. The four
  defensive reactions already do this right (resolution.gd _try_spend_reaction → spend_reaction).
  Verified against post-Iteration-G action_economy.gd (2026-07-07): spend_reaction() checks
  only _is_spent; reacting is budget-gated, never turn-action-gated. Do NOT regress this.
